# Providers

favo supports Claude Code, Codex, Antigravity CLI and OpenCode. Adding one is a table entry in `packages/domain/src/providers/provider.ts` plus a shim in `apps/server/src/modules/providers/gateways/`.

## What was learned from the real CLIs

Test a provider on the real binary before changing its entry. Documentation has been wrong here more than once.

| Provider    | Facts                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude Code | `CLAUDE_CONFIG_DIR` separates the login. On macOS the keychain entry is tied to the folder path, so moving a folder signs it out. Saving through a linked `settings.json` keeps the link.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Codex       | `CODEX_HOME` separates the login. `codex login status` can say logged in while the token is revoked; `app-server` `account/read` tells the truth, so favo asks that first. Over ssh, login needs `--device-auth` because the localhost callback cannot reach your browser. Plugins cannot be linked: its loader refuses code reached through a link outside its home.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Antigravity | `agy` follows only `HOME`, not `GEMINI_HOME`. There is no login or logout command: launching signs in, and `agy models` is the only status signal. Its login lives in the system keychain under one name for the whole computer, unless `agy` skips the keychain, so `loginScope` is `perComputer` and `loginScopeOf` turns it into `perAccount` where it is skipped. See Antigravity's login below. `agy` saves its own files with `fs.Path.AtomicWrite`, a temp file renamed over the target, so a linked file becomes a copy on its first save: a hard link split on Windows, and on 2026-11-05 `agy mcp add` turned a symlinked `mcp_config.json` into a plain file in WSL, leaving the base alone. | OpenCode    | Move `XDG_DATA_HOME` and `XDG_STATE_HOME`, never `XDG_CONFIG_HOME`, which other tools read (`gh` shows logged out when it moves). `--standalone` is required because the background service has a fixed port. One account holds several logins.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

### Antigravity's login

Run on 2026-11-05 with `agy` 1.4.12 and 1.5.1 on Windows 11 and 1.5.1 in WSL, and read by disassembly from the Linux, macOS x64 and Windows builds of 1.5.1 and the app's 2.29.0 `language_server`. No Google account was used: favo never reads a token, so the test planted a fake one.

- **The keychain entry is `gemini:antigravity`** (zalando `go-keyring`, service `gemini`, user `antigravity`), whatever `HOME` is. A fake token written there with `go-keyring` itself reached two seats with different `HOME` and `USERPROFILE`: both answered `Eligibility check failed: UNAUTHENTICATED (code 401)`, against `Please sign in` with no token. The token must say `"auth_method":"consumer"`, or `agy` treats it as signed out.
- **The fallback file is `~/.gemini/antigravity-cli/antigravity-oauth-token`**, so it follows the seat. `NewCompositeTokenStorage` decides once at start and logs `Using file-based token storage because …` in `~/.gemini/antigravity-cli/cli.log`.
- **It skips the keychain** when `SSH_TTY`, `SSH_CLIENT` or `SSH_CONNECTION` is set; when `WSL_DISTRO_NAME` or `WSL_INTEROP` is set or `/proc/sys/kernel/osrelease` holds `microsoft` or `wsl`; when `/.dockerenv` exists or `/proc/1/cgroup` holds `docker`, `containerd` or `kubepods`; on Linux only, when `DBUS_SESSION_BUS_ADDRESS` is empty, `none:` or `disabled:` and the session bus is not a socket, looked for at `$XDG_RUNTIME_DIR/bus` when that is set and not empty, else at `/run/user/<uid>/bus` (run against `agy` 1.5.1 in WSL: a runtime folder without `bus` hides `/run/user/1000/bus`); and for an hour after a keychain timeout, marked by `~/.gemini/antigravity-cli/cache/antigravity-keyring-unavailable`. The D-Bus check compiles to a constant `false` on macOS and Windows (32 bytes, against 160 on Linux). Setting `SSH_CONNECTION` or `WSL_DISTRO_NAME` on Windows really did move `agy` to the file.
- **There is no supported switch.** `NewCLITokenStorage` zeroes the caller's request for a file and never sets it, and the strings hold no setting or variable for it. `AGY_ACCOUNT` picks a plugin account such as `gh`, not the Google login.
- **The timeout marker is off on Windows.** `NewCompositeTokenStorage` reads it only when a package variable is true. That variable is `01` in the Linux build's data and sits in zeroed memory in the Windows build, and nothing writes it. On 2026-11-05 a marker dated now, and one dated 2100, both left `agy` 1.5.1 on Windows reading the keychain. A future-dated marker would have needed no variable, but not on Windows.
- **So every seat gets `WSL_INTEROP`.** `seatVariables` on `Providers.antigravity` puts `WSL_INTEROP=favo` in `isolationEnvironment`, which every favo path to `agy` goes through: launches, sign-in, status, resume and the app. `agy` then keeps the login in the seat's file on every system. `personal` gets nothing and stays on the keychain, where your own `agy` keeps it. An inherited `WSL_INTEROP` wins, because inside WSL it is the interop socket that runs Windows programs, and `agy` there skips the keychain anyway. Chosen over the other skip conditions by reading every user of them in `agy` 1.5.1 and the app's `language_server` 2.29.0: the SSH variables also switch sign-in to pasting a code (`oauthMethod.StartInteractive`), the clipboard to OSC 52 and the remote-session logic, and `WSL_DISTRO_NAME` feeds telemetry and is read by tools such as `wslview`. `WSL_INTEROP` is read only by the keychain detector and two terminal-telemetry labels, and the app's JavaScript reads neither. Run on Windows 11 with a real login in the keychain: a seat without the variable listed the models, the same seat with it said `Please sign in` and logged `Using file-based token storage because WSL environment detected`.
- **The app keeps its own login per seat.** With the variable, the app's `language_server` uses `~/.gemini/jetski-standalone-oauth-token`, a different file from `agy`'s, so `DesktopAppSpecs.antigravity` is `separate` with that `loginFile`, and `desktop.login` answers from whether it exists. `personal` follows `agy`'s status, because there both read the keychain. Hard-linking the two files would let them share one login (`agy` writes with `os.WriteFile`, in place, and a hard-linked fake token reached the app on Windows), but a sign-out deletes only one name, so favo would sign it back in on the next link. Not done.
- **T3 Code is not covered.** It launches `agy` with only the seat's `HOME`, so `agy` there still reads the keychain. Set `WSL_INTEROP=favo` in T3 Code too, if it lets you.
- **`perComputer` and `unverified` stay in `LoginScope`** only because favo 0.10.0 and older send them. Every Antigravity seat is now `perAccount`, and the keychain detection that 0.10.0 used to decide `perComputer` is gone.

## Limits

`ProviderCli.limits` reads limits through the official CLI, never a token. Claude Code and Codex override it; the default answers `unsupported`, so OpenCode and Antigravity need no code. Verified on 2026-11-01 on real seats with Claude Code 2.1.316 and Codex 0.164.0: both answered in about 2 seconds with their own numbers, and no thread, project folder or process stayed behind.

- **Claude Code:** `claude -p --input-format stream-json --output-format stream-json --verbose --no-session-persistence --setting-sources local`, then `initialize` and `get_usage` with `skip_behaviors: true` as `control_request` lines. Nothing is sent to a model. This is an unstable API the Agent SDK marks experimental, so parse loosely and turn anything unexpected into `probeFailed`. `resets_at` has microseconds and an offset, so normalize it. `model_scoped` holds the per-model weeks.
- **Claude Code environment:** an `ANTHROPIC_API_KEY` around makes a subscription seat look like an API key seat, so `limitsEnvironment` clears every `CLAUDE*`, `ANTHROPIC*` and `HERDR*` variable, then the seat's own `CLAUDE_CONFIG_DIR` goes back in. The login check of a read uses that same environment, or a shell started inside one seat reports another seat's login. It runs from `~/.favo/empty` so no project settings load.
- **Codex:** `account/rateLimits/read` on `app-server`. `primary` and `secondary` are positions, so read the kind from `windowDurationMins`. `resetsAt` is epoch seconds, unlike Claude. The answer also holds reset credits, which favo ignores. `limitsEnvironment` clears `CODEX_HOME`, for the same reason as Claude's. An API key seat has no limits to read: Codex 0.164.0's binary text says `chatgpt authentication required to read rate limits`, so a refused read asks `account/read` and answers `unsupported` for `apiKey`. That comes from the binary's text and T3, and was not run on a real API key seat.
- **Antigravity:** `agy` was not installed on the machine used, so whether `agy models` reports quota is still unknown.

## Tokens

favo counts tokens from the session logs each provider already writes, never from a token or a request. The readers are pure: `claude-token-log.ts`, `codex-token-log.ts` and `opencode-token-log.ts` in `packages/domain/src/usage`. The first two were ported from T3 Code's readers at commit `7462f23`, and checked on hand-written lines and, for Codex, against the 36 cases of T3's own test file. Neither has been compared with ccusage on a real seat yet. Antigravity is not counted.

- **Claude Code:** every `.jsonl` under `projects/` in the seat's config folder. Count `type: assistant` lines with `message.usage`, once per `message.id` plus `requestId` across every file of the seat, keeping the largest of each number. Logs are deleted after 30 days, which is why favo keeps its own record.
- **Codex:** every `rollout-*.jsonl` and `.jsonl.zst` under `sessions/`. `token_count` carries no model, so it comes from the latest `turn_context`. `input_tokens` includes the cached part. A fork copies its parent's history in a burst, which is skipped. One rule differs from T3 on purpose: when the running total jumps by more than the request an event reports, with nothing to explain the gap, favo counts that request and leaves the gap out, where T3 drops the event and flags it. On a real home on 2026-11-12 that was 10 events in 82,445, hiding 0.9M tokens of requests beside a 13.3M gap, and a warning that never went away.
- **OpenCode:** `opencode.db` in its data folder, which is the seat itself for `personal` and `<seat>/opencode` for a cell, because `XDG_DATA_HOME` is the seat. favo lists that one folder and goes no deeper: it also holds `storage`, `snapshot` and `bin`, 63,627 files on a real home, and walking them took up to a second to find one file. Messages sit in two tables. `message` is 1.x: `data.role` is `assistant` and the model is `data.modelID`. `session_message` is 2.x: `type` is `assistant` and the model is `data.model.id`. 2.x copies the old rows into the new table under the same id, but leaves out the numbers of 1.x compaction messages, so favo reads both tables and counts an id once. Both keep `tokens.input`, `output`, `reasoning`, `cache.read` and `cache.write`, where `input` leaves the cached part out and `output` leaves reasoning out, so favo adds reasoning to output. The model is the bare id, without the provider it was reached through, so a name such as Copilot's `claude-opus-4.6` is unpriced when the price table does not hold it. A message with no tokens is left out. 2.x keeps the text of a message inside `data`, so each number is taken with `json_extract` and the text never leaves SQLite. A session deleted in OpenCode takes its rows with it, and favo's own record keeps what it counted. The JSON files under `storage/`, from before the database, are not read. The read is synchronous in `bun:sqlite`, so the gateway gives the turn back every 50 milliseconds, by the clock and not by a count of rows, so the number of pauses stays small wherever a pause is slow.
- **OpenCode, as run** on 2026-11-13 against a real `personal` home on macOS, with a database written by OpenCode 1.14 to 2.2.7 and `opencode serve` 2.2.7 running: 71,623 rows in about 2 seconds, the longest pause about 0.1 seconds for one very large row, and 1,823,162,566 tokens, the same as the sum taken by hand with `sqlite3`. The 1.x table matched the `step-finish` rows of the `part` table to the token. The database is in WAL mode and 4.3 GB; opened read-only, its three files kept their dates. Not run on Windows, on a cell other than `personal`, or on a machine that never left 1.x.
- **Only numbers, times, model names and ids are read.** A change that needs any other field of a log line needs a new decision, not a new field.

## Threads and hooks

A hook tells favo the thread while the provider runs. Each provider is a `hook` entry in `Providers`, and every one ends at `favo hook <provider> <owner>`, which reads stdin, saves `~/.favo/threads/<account>/<provider>/<id>.json` and exits 0 with nothing printed. One file per thread means hooks at the same moment cannot lose each other's writes. The hook line starts favo only when `FAVO_ACCOUNT` is set, so a provider run outside favo never starts it, and a missing favo stays silent.

Verified on 2026-11-01 in a throwaway `HOME` with a local mock model server, on Claude Code 2.1.316, Codex 0.164.0, OpenCode 2.2.5 and 1.19.5, and Herdr 0.9.5. Do it the same way: no quota is spent and your real config stays out of it. Run `pwsh` by hand for the Windows form.

| Provider    | Facts                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude Code | `SessionStart` fires at startup, before anything is said, and leaves no transcript until the first message, so a thread with no `transcript_path` file is empty and hidden. `/clear` gives a new ID with `source: clear`. `--resume` and `--continue` keep the ID with `source: resume`. `CLAUDE_CODE_CHILD_SESSION=1` and `CLAUDECODE=1` are set even at the top level, so they cannot tell a nested run. `CLAUDE_CONFIG_DIR` decides whose thread it is.                                                                                                                                                                                                                                                                                                                                                                                           |
| Codex       | `SessionStart` fires on the first prompt, not at startup, so an empty session never reaches favo. `/new` gives a new ID but still says `source: startup`, so the source alone cannot tell it from a nested run. Spawned subagents fire `SubagentStart`, never `SessionStart`. Hooks are stable and on by default, so favo never edits `config.toml`. Hooks run in `$SHELL -lc` and `cmd.exe /c`, which is why the POSIX line wraps itself in `sh -c` for a fish user. The trust key is `<CODEX_HOME>/hooks.json:session_start:<group>:<handler>`, so each seat asks once and favo must add its entry after the others, never before them. An edit to the hook asks again. `codex exec` skips an untrusted hook with no message. Rollouts open with a `session_meta` line holding `cwd`, then a very long `base_instructions`, so read only the head. |
| OpenCode    | A plugin is a default export with `{ id, setup }` on 2.x and `{ id, server }` on 1.x, and the same file carries both. An `export const` plugin does not load on 2.x. The plugin runs in the `serve` child with `FAVO_ACCOUNT` visible, so `process.pid` is the owner. A `personal` seat uses the background service, which has no `FAVO_ACCOUNT`, so it falls back to `opencode session list`, which only sees the current folder. `opencode run` is not recorded, and nobody goes back to one.                                                                                                                                                                                                                                                                                                                                                      |
| Antigravity | Copied from Herdr's integration and **not run**: `agy` was not installed. A named block in `.gemini/config/hooks.json`, `PreInvocation` after the first prompt with `conversationId`, `{}` expected on stdout, and `--conversation <id>` to resume.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

- **A nested run** is told by the process, not by the source. The hook sends `$PPID`, and a fresh start is ignored while another process that reported for that launch is still alive. A login shell that forks instead of replacing itself, such as bash with an `EXIT` trap, leaves a `$PPID` that is already gone, so it never counts. On Windows there is no cheap parent, so a nested run there adds a thread to the list. It never replaces one.
- **A second provider inside a seat** inherits `FAVO_ACCOUNT` but runs on another home, so `record` compares what `isolationEnvironment` sets with the real path. Antigravity needs the real path, because it runs with `HOME` on the seat and reaches `~/.favo` through the mirrored link.
- **Windows** uses `powershell -EncodedCommand`, because the same line has to survive both `cmd.exe` and Git Bash. Anything after the base64 makes PowerShell refuse to start, so the version marker lives inside the encoded script. Windows PowerShell 5.1 re-encodes a pipe as US-ASCII, which turns an accent in a folder into `?`, so the script sets `$OutputEncoding` to the console's input encoding and the bytes pass through unchanged.
- **Changing the hook** means raising `HookVersion` and the number in `opencode-plugin.txt`. Do it sparingly: it makes Codex ask every seat again.

### Herdr

Herdr 0.9.5 accepts `--source favo --agent claude` with nobody holding the pane, once it sees that agent, and it does see it under `favo`. A fresh Claude Code start can beat that: on 2026-11-01 a report sent a second after launch was refused with `resume_not_accepted`, and the same report was accepted seconds later. Do not remove the retry on the strength of a run that looks fine, because it hides this. Log what Herdr answers instead, by setting `HERDR_BIN_PATH` to a wrapper on the launch line. A refused report hands off to a detached `favo hook <provider> --report <id>`, so the provider never waits. Without it Herdr keeps only its own record, and the pane restarts outside the seat. Every report needs a rising `--seq`, in microseconds, and a release needs one taken when it runs, which is what `stampFlag` is for. Reported command is `favo resume <provider> <folder name> <id>`: the folder name survives a rename, and a thread with no messages starts the seat fresh instead of failing.

A release is not optional. Without it, the command stays in the pane for as long as it is not back at an idle shell, which is always the case in the TUI. To test: `herdr --session <name>` in the lab `HOME`, then `herdr session stop <name>` and start it again. OpenCode and Antigravity are not reported, because Herdr's own hooks hold those panes and favo's report would be refused. Remote seats are not reported yet, because `HERDR_*` is not set on the other machine.

## Updates

`favo update` runs in two processes, because a machine is installed from the release of the favo that installs it. The first runs the package manager. The new binary then does the rest, started as `favo update --skip-favo`. **An old favo starts a newer one with that flag, so a new version must always accept `--skip-favo`, `--favo-only` and `--machine local`.** A remote machine gets those same arguments over `ssh -t`, so there is no remote case for providers. Plain `favo update` stops after favo is current on every machine, and `--providers` goes on to the provider CLIs. `--skip-favo` on its own still means the provider CLIs too, because favo 0.5.0 sends it that way: when it restarts the new binary after its upgrade, and when its `P` asks a newer machine over ssh. A new favo restarting itself after a plain `favo update` adds `--favo-only`. A restart always runs the same or a newer binary, so the opt-out is safe.

Own command and package manager both run with the package manager's folder first on `PATH`: Codex and Claude Code find `npm` through `PATH`, and an npm script runs whichever `node` comes first. Only a path a package manager holds under a name in `update.packages` counts as that install. A `mise` shim resolves to the `mise` binary, so without that list favo would upgrade `mise`.

**The fallback runs only on a non-zero exit, because exit 0 proves nothing.** `claude update` exits 0 when it refused. Comparing versions cannot tell that from up to date, and running the package manager then would override a provider that turned updates off.

Tried on 2026-11-02 in a throwaway `HOME` with stand-in `brew` and `npm` that log their arguments, on Claude Code 2.1.316, Codex 0.166.0 and OpenCode 2.2.5. Do it the same way, with a copy of the binary under a lab prefix: its package manager folder comes first on `PATH`, so a real `/opt/homebrew` path runs your real `brew`.

| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude Code | Despite its help, it never runs a package manager on Homebrew: it prints `To update, run: brew upgrade <cask>` and exits 0, hence `refusedOn`. Read from the binary: winget and apk print the same. The cask is `claude-code@latest` or `claude-code`. `DISABLE_UPDATES` refuses with exit 0, and `DISABLE_AUTOUPDATER` does not stop `claude update`, but favo honors both. `autoUpdates: false` lives in `.claude.json`, which holds the login and can hold MCP server keys, so favo does not read it for updates; the only read of that file is `oauthAccount.accountUuid`, under Desktop apps. The cask is `antigravity-cli`, with `auto_updates true`. `agy --help` in 1.4.12 and 1.5.1 lists `update` and `install` commands, but `update.arguments` is still unset, so `favo update` goes straight to the package manager; run `agy update` before changing that. Its background updater replaces the shared binary even from a seat: on 2026-11-05 one `agy models` in a test `HOME` moved `%LOCALAPPDATA%\agy\bin\agy.exe` from 1.4.12 to 1.5.1.                                                                       |

**Homebrew refreshes a third-party tap only when it updates itself.** Read on 2026-11-04 from `Library/Homebrew/utils/auto-update.sh` and `cmd/update.sh` on Homebrew's main branch, not run on a Mac: before `upgrade`, Homebrew runs `brew update --auto-update` only when the brew repository's `FETCH_HEAD` is older than `HOMEBREW_AUTO_UPDATE_SECS`, 86400 by default, or 300 when the argument names a tap as `owner/tap/name`. Formulas and casks from homebrew-core and homebrew-cask come from the JSON API, which refreshes on its own every 450 seconds, but `irwinarruda/tap` is a git clone, so `brew upgrade favo-cli` missed a release for up to a day. Every Homebrew step favo runs, and the provider's own command when Homebrew holds it, gets `HOMEBREW_AUTO_UPDATE_SECS=0` and loses `HOMEBREW_NO_AUTO_UPDATE`, which is the same as `brew update` first. `brew list --pinned` is not an auto-update command, so it stays fast.

The comb reads versions through `updates.listVersions`, a machine method that runs only `--version`, never `brew list --pinned` or `which`. An older favo answers `unknownMethod`, which the comb shows as `older favo`, so the new method needed no `Protocol` bump. The last update of each provider is `~/.favo/updates/<provider>.json`, one file per provider, written by the favo that runs the update through `updates.record`: `updating` before the steps, then `failed` with its exit code, `stopped` on Ctrl-C, or `leftAlone` with the reason favo printed. An update that worked deletes the file, so only what needs a look stays. `updating` keeps the pid of that favo, and reads as `stopped` once the process is gone, so a closed terminal does not leave it updating forever.

The comb's `P` never hands the terminal over. `updates.start`, a machine method, starts `favo update --skip-favo --machine local --provider <id>…` with `detach` on each machine and writes `updating` for every chosen provider with the pid `detach` returns, not its own: the backend of a remote comb is a `serve --stdio` that ends with the TUI, and the update must not read `stopped` while it still runs. The detached favo has no TTY, so `ask` answers no and a running provider is left alone with `RunningReason`; the comb offers those again and starts them with `--update-running`. The pid is written right after `detach`, before the new favo has listed anything, which takes it far longer. A provider whose record is already `updating` with a live pid is skipped, so a second comb, or one reopened mid-update, never starts a second package manager on it; the comb follows it instead. `updates.start` answers with the providers it started and their versions, which is what the comb sums up. While a provider is `updating`, `updates.listVersions` keeps it even when its binary is gone, as `being replaced by its update`, because a package manager can unlink it for a moment. A request over SSH times out after 45 seconds, so the comb never waits on the update itself: it reads `updates.listVersions` every 2 seconds until nothing is `updating`, for at most 15 minutes, and then says what is still updating. An older favo answers `unknownMethod`, so the comb updates favo there first, as `favo update --providers` does. Run on 2026-11-06 with the Linux build in a lab `HOME` with stand-in `claude` and `codex` scripts and nothing else on `PATH`: both read `updating` at once and settled one by one, a pid file under `running/` left Claude alone until `--update-running`, and quitting the TUI mid-update left the detached favo to finish and record.

The npm launcher sets `FAVO_LAUNCHER` and `FAVO_LAUNCHER_NODE`, because the binary lives in `~/.favo/runtime/<version>` and cannot tell where npm put the launcher. Those are trusted only for a binary under `runtime`, so a provider started by an npm favo cannot make a Homebrew favo run npm. `FAVO_LAUNCHER` is `process.argv[1]`, not `import.meta.filename`: pnpm's real path holds the version, so restarting through it would run the old favo. favo resolves it to find the install and restarts through it as given.

A symlink resolves to the install, a script does not. Windows npm and pnpm leave one, so favo reads its head for `node_modules/<package>`. `mise` and `asdf` shims hold no such path, so those installs have the provider's own command and no fallback. Ctrl-C reaches the child, which exits 130, and that stops the whole run instead of starting the package manager. Exit codes for Ctrl-C on Windows were not checked.

Off switches come from the caller's environment and from the login shell, which is what `LoginShellEnvironment` probes for `UpdateVariables`, because `ssh -t` loads no `.zshrc`. Claude Code counts `1`, `true`, `yes` and `on` as set: `DISABLE_UPDATES=0` does not stop it, run on 2.1.316.

"Running through favo" is a pid file at `running/<account>/<provider>/<launch>`, written by `runTerminalPlan` around the child. It is not the hooks, which are optional, and not a process scan, which cannot tell a favo launch from any other. A file whose process is gone is deleted when read.

## Desktop apps

`DesktopAppSpecs` in `packages/domain/src/desktop/desktop-app.ts` is a table entry like `Providers`. Each app is a window plus the agent it runs, and favo gives each its own folder in the seat: the window's is `accounts/<account>/<profileFolder>`, set with `--user-data-dir`, and the agent's is the seat, set with `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, or `HOME` and `USERPROFILE` for Antigravity. `personal` passes nothing, so it is the default folder, which `DesktopApps.defaultProfile` names for each system. `desktop.open` is a `hub` method, because the window opens on the computer you are at. Over SSH, `SshDesktopApps` wraps the system's gateway: it finds apps and names their default folders as on that computer, and refuses to open, close or look for a window, since an SSH session reaches no screen. Each listed app carries `canOpen`, so a favo run inside SSH still shows app logins but offers no `p`. Linux without a display and outside SSH still gets `HeadlessDesktopApps`.

### Logins

`login` on each spec says where the app keeps its sign-in. `sharedWithCli` means the app signs in through the seat's CLI, so the comb's CLI status is the whole answer. `separate` means the app has a login of its own, which the comb shows beside the CLI's through `desktop.login`. `desktop.list` and `desktop.login` are machine methods, so each seat's app is listed and read on the seat's own machine and a remote hive shows its app. An older remote shows no app rather than an error, with no `Protocol` bump: 0.7.0 used `HeadlessDesktopApps` over SSH and lists nothing, and anything older answers without `canOpen` or with an unknown method, which the comb reads as no app.

**favo reads two things, and nothing else.** Decided on 2026-11-04 in #27, because nothing else tells signed in from signed out: the uuid folder names outlive a sign-out. From `<profile>/config.json`, favo keeps only `windowSizeWasSignedIn` and `lastKnownAccountUuid`. From the seat's `.claude.json`, or `~/.claude.json` for `personal`, it keeps only `oauthAccount.accountUuid`, which `claude auth status` does not give. Nothing else from either file is logged, returned or stored, and `desktop.login` answers only the state and whether the two uuids differ. These are the only reads of an app's folder. Comparing organizations instead does not work: the app's current one is in an encrypted cookie, and the `dxt:allowlist*:<orgId>` keys list every organization ever used.

`appLoginOf` decides. No profile folder means the app never opened as that seat, so signed out, because favo makes that folder when it opens the app. The default folder of `personal` belongs to the app, and favo may be looking in the wrong place (the Linux path is unchecked, and the Windows app moved it once), so a missing one is unknown. `open` makes a seat's folder before the first launch, so a seat reads unknown from then until its first sign-in. A missing, mistyped or unreadable flag is unknown, never signed out, because the flag is an internal detail an update can rename. Another account needs both uuids, and the comb shows it only while the CLI is signed in too. The flag reflects the app's last run, so a login revoked while the app was closed still reads signed in. While its window is open, the app writes the flag from a watcher on its account state (`T5n` inside `Xl`, found by searching `resources/app.asar` of Windows build 4.16336.0 for the key on 2026-11-04), so a sign-in reaches `config.json` at once. That is what lets the comb, after `p`, read that seat every 3 seconds for 3 minutes until the app is signed in, stopping early when another seat is opened, the seat goes away or a read fails.

## Windows

Tested on Windows 11 with real binaries.

- Symlinks need Developer Mode or admin; without them they fail with `EPERM`. Folders use junctions and files fall back to hard links, in `NodeFileSystem`. A hard link has no target, so "linked" means same file identity (`Entry.identity`).
- A save that renames over a hard link splits it. That is reported as a conflict, never repaired by overwriting.
- A home folder holds the registry (`NTUSER.DAT` and friends). `mirrorEntries` must never touch them.
- The variable is `Path`, not `PATH`, so environments merge through `mergeEnvironment`.
- npm installs `.cmd` shims, which only run through `cmd.exe`; `spawnCommandOf` handles it, and refuses an argument with a character `cmd.exe` would interpret. Do not add escaping: refusal is the safe failure.
- `cmd` errors are translated, so never match their text. Use exit codes.
- OpenSSH for Windows mangles a command that starts with a bare `cmd`: `cmd /c ver` fails and `cmd.exe /c ver` works. Always write `cmd.exe`.
- In `cmd`, `if a b & c` runs `c` inside the `if`. Wrap each conditional in parentheses.
- A running `.exe` cannot be overwritten, but it can be renamed.
- Claude installs to `~/.local/bin`, off the PATH, so favo adds that folder. npm's OpenCode is 1.x, with no `--standalone` and a different `auth list`.

Run `bun test` on Windows too. `cmd.exe` and NTFS have caught what no Unix test could.

## Checklist

1. Shared is an allowlist. Never add a credential, a session or a cache.
2. Status never reads a token's value. Beyond the official status commands, a login is read only through the three fields named under Desktop apps, and nothing else from those files is kept.
3. Never move a seat folder. A rename only changes `accountNames` in `config.json`, because the keychain login and the path pasted into T3 Code both depend on the folder.
